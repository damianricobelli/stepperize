Stepperize can validate a step's data without becoming a form library, and
without tying you to one validation library. This page explains how, and the
one distinction that makes it click: **what a step stores is a draft, and the
validated output is kept next to it**.

<FrameworkOnly is="angular">
On this page, `stepper` is the value of the signal `injectStepper()` returns:
`this.stepper()` in a class, `stepper()` in a template.
</FrameworkOnly>

<FrameworkOnly is="lit">
On this page, `stepper` is the controller's `value`: `this.stepper.value`.
</FrameworkOnly>

## Standard Schema, not a specific library

A step may carry a `schema`. Any [Standard Schema](https://standardschema.dev)
works, so Zod, Valibot and ArkType are interchangeable, and can even be mixed
in one flow.

<FrameworkCode>

```tsx framework="react" title="checkout.ts"
import { defineStepper } from "@stepperize/react";
import { type } from "arktype";
import * as v from "valibot";
import { z } from "zod";

export const checkout = defineStepper([
  { id: "shipping", schema: z.object({ address: z.string().min(1) }) }, // Zod
  { id: "payment", schema: v.object({ card: v.pipe(v.string(), v.nonEmpty()) }) }, // Valibot
  { id: "review", schema: type({ accepted: "boolean" }) }, // ArkType
]);
```

Stepperize has no dependency on any of them. It only reads the `~standard`
property every compliant schema exposes.

A schema does two things for its step:

1. **It types the step's data.** `stepper.data.shipping` is the schema's input
   type, and so is the argument of `setData("shipping", ...)`.
2. **It is what `next()` validates.** A step that fails its schema cannot be
   left through `next()`.

## What next() does

<FrameworkCode>

```ts framework="react vue svelte solid"
const result = await stepper.next({ address });
```

```ts framework="angular"
const result = await this.stepper().next({ address });
```

```ts framework="lit"
const result = await this.stepper.value.next({ address });
```

</FrameworkCode>

1. Takes the data you pass as the data of the current step. Without an
   argument, it takes what the step already has stored.
2. Validates it against the step's schema. Async schemas are awaited.
3. If it is valid, marks the step [complete](/docs/v9/:framework/concepts/step-state)
   and moves on.
4. If it is not, stays on the step, keeps the data you passed, and remembers
   the issues.

<FrameworkOnly is="vue">
The flow keeps the object it is given. Pass a copy of a `reactive` object
(`{ ...values }`), not the object itself: later edits to the form would
otherwise change the step's data behind the flow's back.
</FrameworkOnly>

<FrameworkOnly is="svelte">
The flow keeps the object it is given. Pass plain data with
`$state.snapshot(values)`, not the `$state` proxy: later edits to the form
would otherwise change the step's data behind the flow's back.
</FrameworkOnly>

<FrameworkOnly is="solid">
The flow keeps the object it is given. Pass a copy of a store (`{ ...values }`,
or `structuredClone(unwrap(values))` when it is nested), not the store itself:
later edits would otherwise change the step's data behind the flow's back.
</FrameworkOnly>

<FrameworkOnly is="angular">
`getRawValue()` of a form group is already a plain object, so it can go to
`next()` as it is.
</FrameworkOnly>

<FrameworkOnly is="lit">
`Object.fromEntries(new FormData(form))` gives every field as a string. Let the
schema coerce what should be a number or a boolean: the draft keeps what was
typed, and the output has the right types (see
[draft data and validated output](#draft-data-and-validated-output)).
</FrameworkOnly>

It never throws for an invalid step:

```ts
if (!result.accepted && result.reason === "invalid") {
  result.issues; // [{ message: "Address is required", path: ["address"] }]
}
```

Validation runs for `next()` only. `prev()` and `goTo()` leave a step without
checking it, which is why going back is never blocked by a half-filled form.

## Show the issues

`issues(id?)` returns the issues of the last rejected `next()` for a step, the
current one by default. They are cleared as soon as that step's data changes,
so an error goes away when the person starts fixing it.

<FrameworkCode>

```tsx framework="react" title="Errors.tsx"
function Errors() {
  const stepper = checkout.useStepperContext();
  return (
    <ul>
      {stepper.issues()?.map((issue, index) => (
        <li key={index}>{issue.message}</li>
      ))}
    </ul>
  );
}
```

## Draft data and validated output

`stepper.data` holds whatever each step last saved. It is a scratchpad, typed
as the schema's **input**, and it may be partial or invalid at any time.

| | `stepper.data.shipping` | `stepper.output.shipping` |
| --- | --- | --- |
| **What it is** | The stored draft | What the schema produced when `next()` completed the step |
| **Typed as** | Schema input, or `undefined` | Schema output, or `undefined` |
| **Guarantees** | None | Parsed and valid; present only while the step is complete |
| **Use it for** | Filling forms, saving drafts | Submitting, review screens that show the final values |

Stepperize does not replace the draft with the schema's output: your fields
keep reading what the person typed. The output lives in `stepper.output`, so a
schema that transforms or coerces (trimming, string to number, defaults) never
has to be run a second time by you.

```ts
const shippingSchema = z.object({
  zip: z.string().trim().regex(/^\d{5}$/),
  floor: z.coerce.number().default(0),
});

await flow.next({ zip: " 90210 ", floor: "3" });

flow.data.shipping; // { zip: " 90210 ", floor: "3" }: as typed
flow.output.shipping; // { zip: "90210", floor: 3 }: as validated
```

The same output is the first argument of `onFinish`, and what a
[`next` branch](/docs/v9/:framework/guides/branching) receives for the step being
left:

<FrameworkCode>

```ts framework="react vue svelte solid"
const stepper = checkout.useStepper({
  onFinish: (output, data) => {
    api.createOrder(output); // every complete step, validated
    data; // every step as typed, complete or not
  },
});
```

```ts framework="angular"
export class Checkout {
  readonly stepper = checkout.injectStepper({
    onFinish: (output, data) => {
      api.createOrder(output); // every complete step, validated
      data; // every step as typed, complete or not
    },
  });
}
```

```ts framework="lit"

    onFinish: (output, data) => {
      api.createOrder(output); // every complete step, validated
      data; // every step as typed, complete or not
    },
  });
}
```

</FrameworkCode>

A step has output only while it is complete. Change its data and both go away
until `next()` validates it again. Steps that were
[restored](/docs/v9/:framework/guides/persistence) as complete have none until the
flow finishes: a snapshot stores the draft, and `next()` on the final step
validates those steps once more before calling `onFinish`. If one of them no
longer passes, for example because the schema changed since the draft was
saved, the flow does not finish: the result is `invalid`, and
`stepper.issues(id)` has the issues for that step.

## Steps without a schema

They are first-class. Their data is typed `unknown`, and `next()` always
passes them. Intros, confirmations and review screens need nothing more.

```ts
const wizard = defineStepper([
  { id: "intro" }, // next() always moves on
  { id: "details", schema: detailsSchema }, // validated
]);
```

## Async validation

A schema can be asynchronous, for example to ask the server whether a username
is free. `next()` awaits it, `stepper.isPending` is `true` meanwhile, and other
moves are refused with `reason: "pending"`.

```ts
const account = z.object({
  username: z
    .string()
    .min(3)
    .refine(async (value) => !(await api.isTaken(value)), "That username is taken"),
});
```

Synchronous schemas never set `isPending`, so there is no flicker.

<FrameworkOnly is="angular">
An async schema replaces an async validator for the step: `next()` waits for
it, and `stepper().isPending` is what disables the Continue button. The form's
own `pending` status does not know about it.
</FrameworkOnly>

## Validate without moving

`stepper.validate()` runs the schema of the current step on its stored data
and stays where it is. It resolves with the issues, or `undefined` when the
data is valid.

<FrameworkCode>

```tsx framework="react"
async function onBlur() {
  stepper.setData("shipping", values);
  const issues = await stepper.validate();
  if (issues) showErrors(issues);
}
```

```vue framework="vue" title="ShippingStep.vue"
<script setup lang="ts">
import { reactive } from "vue";
import { checkout } from "./checkout";

const stepper = checkout.useStepperContext();
const values = reactive({ address: "", ...stepper.data.shipping });

async function onBlur() {
  stepper.setData("shipping", { ...values });
  await stepper.validate(); // stepper.issues() now holds the result

<template>

  </label>
  <p v-for="(issue, index) in stepper.issues()" :key="index" role="alert">{{ issue.message }}</p>

```

```tsx framework="solid" title="ShippingStep.tsx"
import { createStore } from "solid-js/store";
import { checkout } from "./checkout";

export function ShippingStep() {
  const stepper = checkout.useStepperContext();
  const [values, setValues] = createStore({ address: "", ...stepper.data.shipping });

  async function onBlur() {
    stepper.setData("shipping", { ...values });
    await stepper.validate(); // stepper.issues() now holds the result
  }

  return (
    <>
      <label>
        Address
        <input
          value={values.address}
          onInput={(event) => setValues("address", event.currentTarget.value)}
          onBlur={onBlur}
        />
      </label>
      <For each={stepper.issues()}>{(issue) => <p role="alert">{issue.message}</p>}</For>
    </>
  );
}
```

```ts framework="lit" title="shipping-step.ts"

  #check = async (event: FocusEvent) => {
    const address = (event.target as HTMLInputElement).value;

```

</FrameworkCode>

The result is remembered the same way a rejected `next()` is, so
`stepper.issues()` returns those issues on the next render, until the data
changes. Pass an id to check another step, for example every step from a
review screen:

<FrameworkCode>

```ts framework="react vue svelte solid"
async function checkAll() {
  for (const step of stepper.steps) {
    const issues = await stepper.validate(step.id);
    if (issues) return stepper.goTo(step.id);
  }
}
```

```ts framework="angular"
async checkAll() {
  const stepper = this.stepper();
  for (const step of stepper.steps) {
    const issues = await stepper.validate(step.id);
    if (issues) return stepper.goTo(step.id);
  }
}
```

```ts framework="lit"
async #checkAll() {
  const stepper = this.stepper.value;
  for (const step of stepper.steps) {
    const issues = await stepper.validate(step.id);
    if (issues) return stepper.goTo(step.id);
  }
}
```

</FrameworkCode>

`validate()` only checks. It does not mark the step complete, does not run the
guard and does not call `onChange`: completing a step is what `next()` does.

It validates what the flow has stored, so save the values first with `setData`
when they live in your form library. To check a value that is not in the flow
at all, use the schema you already have: `shippingSchema.safeParse(values)`.

## Checks that are not a schema

For anything a schema cannot express (a server-side rule, a confirmation), use
a [guard](/docs/v9/:framework/guides/navigation#guard-a-move). It runs after
validation and can refuse the move (`reason: "guard"`).

## What validation is, and is not

<CheckList>
  <CheckItem>It tells you whether a step's data satisfies its schema, and blocks `next()` when it does not.</CheckItem>
  <CheckItem>It returns the issues, and keeps them available through `issues()`.</CheckItem>
  <CheckItem>It works with any Standard Schema, with no runtime dependency.</CheckItem>
  <CrossItem>It does not render errors, track touched or dirty fields, or register inputs. That is your form library's job, or a few lines of your own.</CrossItem>
  <CrossItem>It does not make Stepperize a form library. Stepperize owns the flow; validation is the gate between two steps.</CrossItem>
</CheckList>
