Stepperize is for flows where someone moves through named steps: checkout,
onboarding, surveys, import wizards, approval flows and multi-step forms.

You describe the steps once. The definition gives you a typed, reactive
stepper, a provider and a set of accessible, unstyled components that all share
the same step ids.

```tsx
import { defineStepper } from "@stepperize/solid";
import { Match, Switch } from "solid-js";
import { z } from "zod";

const checkout = defineStepper([
  { id: "shipping", title: "Shipping", schema: z.object({ address: z.string().min(1) }) },
  { id: "payment", title: "Payment", schema: z.object({ card: z.string().length(16) }) },
  { id: "review", title: "Review" },
]);

function Checkout() {
  const stepper = checkout.useStepper({ onFinish: (output) => placeOrder(output) });

  return (
    <section>
      <h2>{stepper.current.title}</h2>

      <Switch>
        <Match when={stepper.current.id === "shipping"}><ShippingForm /></Match>
        <Match when={stepper.current.id === "payment"}><PaymentForm /></Match>
        <Match when={stepper.current.id === "review"}><Review data={stepper.data} /></Match>
      </Switch>

      <button type="button" disabled={stepper.isFirst} onClick={() => stepper.prev()}>
        Back
      </button>
      <button type="button" onClick={() => stepper.next(readForm())}>
        {stepper.isLast ? "Place order" : "Continue"}
      </button>
    </section>
  );
}
```

## Is it a form library?

No. Stepperize owns the **flow**: which step is current, moving between steps,
what each step saved and which steps are complete. Your signals, a store or
your form library own the fields. See [Forms](/docs/v9/solid/guides/forms).

## What you get

- **One call moves forward.** `next(data)` saves the step's data, validates it
  against the step's schema and moves on. It resolves with what happened
  instead of throwing.
- **Typed everywhere.** Step ids, each step's data and your own fields
  (`title`, `icon`, anything) are inferred from the definition.
- **Fine-grained.** The stepper is a reactive object, like props: JSX, memos
  and effects follow exactly what they read.
- **Branching as data.** A `next` map decides where each step leads from its
  validated data, and a flow can have more than one ending.
- **Resumable.** One `snapshot` goes in, one `onChange` comes out. The current
  step can follow the URL with a single option.
- **Accessible primitives.** Roles, keyboard navigation, focus and
  announcements are handled for you.
- **Server rendering.** It renders in SolidStart and hydrates in place.
- **Small.** About 3.3 KiB for the stepper and 6.8 KiB with the primitives,
  min + gzip, with no third-party dependencies.

## The same flow as every other binding

The state machine is [`@stepperize/core`](/docs/v9/core), shared by every
binding, so the concepts are the same everywhere. Each has its own page,
with Solid code: [steps](/docs/v9/solid/concepts/steps),
[the lifecycle of a move](/docs/v9/solid/concepts/moves),
[step state](/docs/v9/solid/concepts/step-state),
[validation](/docs/v9/solid/guides/validation),
[branching](/docs/v9/solid/guides/branching) and
[persistence](/docs/v9/solid/guides/persistence).
